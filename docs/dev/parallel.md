# Параллельная работа исполнителей

Для крупной пачки независимых правок (разные файлы, разные части системы) — быстрее, чем по очереди.

1. **План.** Помощник `architect` пишет короткий план (`.claude/agents/architect.md`); пользователь одобряет. В плане части делятся так, чтобы
   они не трогали одни и те же файлы (бэкенд / фронт / приложение / документы — разные исполнители).
2. **Каталоги.** На каждую часть — отдельная рабочая копия и ветка:
   ```bash
   git fetch -q origin && git worktree add /tmp/wt/<имя> -b work/<имя> origin/main
   ```
   Исполнитель (`.claude/agents/executor.md`) работает только там. Фронт: в `/tmp/wt/<имя>/frontend` нужен свой `npm ci`.
3. **Запуск.** Несколько вызовов `Agent` с `subagent_type: executor` в одном сообщении — они идут параллельно. В поручении: ветка, часть задачи, разрешённые файлы.
4. **Слияние** (делает основной Claude, не исполнители): `git checkout main && git pull`, затем по очереди `git merge --no-ff work/<имя>`;
   конфликт — разобрать вручную, не «побеждать» чужие правки. Общие файлы (`news.js`, `changelog.md`, `CLAUDE.md`) правятся только после слияния, одним коммитом.
5. **Проверка:** `set -o pipefail; ./deploy/check.sh` на слитом результате → помощник `reviewer` на весь диф → пуш → проверка выкатки (`docs/dev/outside.md`, «После выкатки»).
6. **Уборка:** `git worktree remove --force /tmp/wt/<имя> && git branch -D work/<имя>`.

Не параллелить: миграции БД (порядок важен), правки `deploy/update.sh`, версии приложений, всё, что меняет один и тот же файл.
